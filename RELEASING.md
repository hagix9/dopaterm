# Releasing Dopaterm

This document defines how Dopaterm releases are made. It is written for humans **and** for coding agents (Codex, Claude, etc.). If you are an agent: follow it literally, and when a rule here conflicts with convenience, the rule wins. If a step cannot be completed, **stop and report** — do not improvise.

The goal is one thing: **release provenance must stay unambiguous.** Anyone must be able to answer "which exact source commit produced this binary?" with a single commit SHA.

## 1. Absolute rules

### 1.1 Version consistency

For every official release, **all** of the following must carry the same version `X.Y.Z`:

```text
package.json version
package-lock.json root version   (both "version" and packages[""].version)
Git tag                          vX.Y.Z
GitHub Release                   vX.Y.Z
artifact filename version
packaged application internal version
```

Example for `0.2.2`:

```text
package.json        0.2.2
package-lock.json   0.2.2
tag                 v0.2.2
GitHub Release      v0.2.2
DMG                 Dopaterm-0.2.2-macos-arm64.dmg
ZIP                 Dopaterm-0.2.2-macos-arm64.zip
installer           Dopaterm-0.2.2-windows-x64-installer.exe
portable            Dopaterm-0.2.2-windows-x64-portable.exe
internal version    0.2.2
```

### 1.2 One release = one source commit

Every artifact of a release is produced from **the same public commit**, and that commit is the one the tag points to.

```text
Release vX.Y.Z
        |
        +-- tag vX.Y.Z
              |
              +-- exactly one public source commit
                    |
                    +-- Source zip        (generated by GitHub from the tag)
                    +-- Source tar.gz     (generated by GitHub from the tag)
                    +-- macOS DMG
                    +-- macOS ZIP
                    +-- Windows installer
                    +-- Windows portable
```

Never build different binaries of one release from different commits. Never build any binary from a commit that is not public on GitHub.

### 1.3 Published releases are immutable

Once a release is published it is **immutable**. If something must change after publication:

```text
DO NOT:
- move or delete-and-recreate the existing tag
  (no `git tag -f`, no `git tag -d` of a pushed tag, no forced or `--delete` push of a tag)
- replace a binary silently
  (no `gh release upload --clobber`, no `gh release delete-asset` on a published release)
- upload a fixed binary under the old version
- add newly built binaries to an old release
- retarget or re-point a published release (no `gh release edit --tag/--target`)
- mix old and new source commits in one release

DO:
- bump the version (patch/minor/major as appropriate)
- create a new commit
- run the tests again
- create a new tag
- rebuild EVERY artifact
- create a new GitHub Release
```

Example:

```text
v0.2.2 published
      |
security bug found
      |
0.2.3 version bump
      |
fix
      |
tests
      |
final public commit
      |
v0.2.3 tag
      |
all artifacts built from that commit
```

GitHub's own "immutable releases" setting is **not** currently enabled for this repository (the v0.2.1 release reports `isImmutable: false`), so nothing technical stops you from editing a release. These rules are the only protection; do not rely on GitHub to stop you. (Enabling that setting is a maintainer decision and could be considered.)

"Only one platform needs the fix" is not an exception: a fix means a new version and a full rebuild. A state such as "macOS has the fix, Windows is the old build" must never exist inside one release.

If a published release is actually harmful (e.g. a leaked secret), the remedy is to **publish a new fixed release and mark the bad one as superseded or withdrawn in its notes**, not to rewrite it. Deleting or editing a release is outside the scope of this document and needs the maintainer's explicit decision.

## 2. Historical exception: v0.2.1

`v0.2.1` has a known, intentional version mismatch:

```text
GitHub Release:             v0.2.1
tag:                        v0.2.1 -> 5b88a98f7726e40f8b7067d36b4ee56c2d324c45
package.json (at 5b88a98):  "version": "0.2.0"
package-lock.json:          0.2.0
artifact filenames:         Dopaterm-0.2.1-...
packaged internal version:  0.2.0
```

This was left on purpose so that the release provenance could be unified on `5b88a98` **without changing that commit**. The v0.2.1 release notes state this openly.

**Do not "fix" v0.2.1.** Do not retag it, rebuild it, re-upload its assets, edit its `package.json`, or edit its release body to hide the mismatch. It is a documented historical exception, not a template.

The version consistency rule (§1.1) applies in full to the **next** official release and every release after it. The next release must have `package.json` and `package-lock.json` bumped **inside its own source commit** (see §3 and §4); the next version must be greater than `0.2.1` (e.g. `0.2.2`), and must not reuse `0.2.0` or `0.2.1`.

## 3. Versioning

Dopaterm uses a practical, simplified SemVer while in `0.x`.

| Bump | Example | Typical content |
|---|---|---|
| PATCH | `0.2.1` → `0.2.2` | bug fix, security fix, small compatibility fix, small change with accompanying documentation |
| MINOR | `0.2.x` → `0.3.0` | substantial new feature, significant behavior addition, major terminal capability |
| MAJOR | `0.x` → `1.0.0` | **Do not bump mechanically.** Only after the maintainer decides a 1.0 policy |

Example of a version judgment (not a promise of any feature): a change that substantially improves the current multi-hop SSH limitation — for instance, enabling OSC 133 integration / Dopaterm effects in an inner shell that the user started by typing `ssh B` by hand — should be evaluated as a **minor release candidate**, not a patch.

### 3.1 Version bump timing

The version bump is **part of the release's source change**, not something bolted on right before building.

```text
decide next version
        |
update package.json
        |
update package-lock.json consistently
        |
implement / finalize changes
        |
tests
        |
final release commit
        |
push main
        |
fresh clone verification
        |
tag the final commit
        |
build all artifacts from the tagged commit
        |
verify
        |
publish Release
```

Code changes after the version bump are fine. What matters is that, **in the final tagged commit**, the versions agree.

Update both files consistently with npm itself rather than hand-editing, for example:

```bash
npm version X.Y.Z --no-git-tag-version
```

`--no-git-tag-version` is required: it edits `package.json` and `package-lock.json` only, and creates no commit and no tag. Review the resulting diff (only the version fields should change) before committing.

Version-consistency check, to be run in the fresh clone (§5), both before tagging and again after the build:

```bash
node -e "const p=require('./package.json'),l=require('./package-lock.json'),v=process.argv[1];process.exit([p.version,l.version,l.packages[''].version].every(x=>x===v)?0:1)" X.Y.Z && echo OK
# prints OK only if package.json, lock "version" and lock packages[""].version all equal X.Y.Z
```

The packaged internal version is checked separately (§7.1).

## 4. Release flow

Short form (details in the sections below):

1. Decide `X.Y.Z` (§3). It must be greater than every existing tag, including burned ones (see below).
2. In the development tree: bump `package.json` / `package-lock.json`, finish the changes, run tests.
3. Commit; push to public `main` with a normal fast-forward push (no force-push, no history rewriting).
4. **Fresh clone** of the public repository into a temporary directory and check out the final commit (§5).
5. In the fresh clone: version check, `npm ci`, tests (§6). Fix problems with a new commit and go back to step 2 — the version is **not** burned yet, because no tag exists.
6. Record the final source commit: `SHA=$(git rev-parse HEAD)`. Verify that it is public: `git fetch origin && git merge-base --is-ancestor "$SHA" origin/main`.
7. In the **same** clone, create and push the tag once. Never use `--tags`, never force:

   ```bash
   git tag -a vX.Y.Z "$SHA" -m "Dopaterm vX.Y.Z"
   git push origin refs/tags/vX.Y.Z
   git ls-remote origin 'refs/tags/vX.Y.Z*'   # the peeled (^{}) line must equal $SHA
   ```

   (Annotated tags are the convention from now on. `v0.2.0` is a lightweight tag and `v0.2.1` is annotated; for an annotated tag the `^{}` / `^{commit}` forms give the commit.) The tag is created once and never moved.
8. Build all artifacts **at the tag** (§7), name them (§8), checksum them (§11). Before **each** build, re-verify in the clone you build from:

   ```bash
   git fetch --tags && git checkout vX.Y.Z
   test "$(git rev-parse HEAD)" = "$(git rev-parse 'vX.Y.Z^{commit}')" && test "$(git rev-parse HEAD)" = "$SHA" && test -z "$(git status --short)" && echo OK
   ```

9. Verify per platform (§9), run the license and secret gates (§12, §13).
10. Create a **draft** Release, upload, verify (§14).
11. Publish. Re-download the public assets and re-verify.

**Burned versions.** A version is burned the moment its tag is pushed, or any Release/draft for it exists. If anything fails after that point: leave the tag and any draft untouched; never publish that draft and never upload to it again; report to the maintainer; bump to the next unused version, make a new commit, and restart from step 2. Deleting a burned tag or draft is a maintainer-only action — an agent must not do it on its own initiative. If a failure occurs *before* the tag is pushed, the version is not burned: add a commit and retry, and do not tag until step 5 passes.

(§5's "equals the tag target" check applies as written only after step 7; before tagging, compare against the recorded SHA.)

## 5. Clean source requirement

Do **not** build official release artifacts directly from a development working tree. The development tree can contain unpushed commits, uncommitted edits, untracked files, local config, and internal notes.

Official releases are built from a fresh clone of the public repository:

```text
1. push the final commit to public main
2. fresh clone from public GitHub
3. check out the release tag, or the full commit SHA
4. `git status --short` is empty
5. `git rev-parse HEAD` equals the tag target
6. npm ci
7. tests
8. build
```

Use an external-SSD temporary directory on the maintainer's Mac (see the repository owner's local agent instructions: large temporary data goes under `/Volumes/VGX1000 SSD/Codex/tmp/`, not under `/tmp`, `/private/tmp`, `/var/tmp` or the home directory; if that location is unavailable, stop and ask). Example:

```bash
WORK="/Volumes/VGX1000 SSD/Codex/tmp/release-X.Y.Z"
mkdir -p "$WORK" && cd "$WORK"
git clone https://github.com/hagix9/dopaterm.git src
cd src
git checkout <full commit SHA or vX.Y.Z>
git status --short           # must print nothing
git rev-parse HEAD           # must equal the recorded final source commit
```

For an annotated tag, compare against the **peeled** commit: `git rev-parse vX.Y.Z^{commit}` (not `git rev-parse vX.Y.Z`, which prints the tag object).

`.gitignore` excludes `node_modules/`, `dist/`, `release/`, `.env*`, `*.pem`, `*.key`, `id_rsa*`, `id_ed25519*` and `.dopaterm-token`. A fresh clone contains none of them, which is exactly why a fresh clone is required. Make sure no untracked files, secrets, HANDOVER/internal reports or temporary files end up in any binary (§13).

A clone is **single-use per release attempt**: never reuse a clone, `node_modules/`, `dist/` or `release/` left over from a failed attempt (git-ignored leftovers are invisible to `git status --short`). Re-run `git status --short` and the HEAD check immediately before and after each `npm run dist:*`; if the status is ever non-empty, stop.

Clean up the temporary directory after the release is complete and no longer needed. Never modify or delete the original development repository as part of that cleanup.

## 6. Test gate

Before the tag is created, run in the fresh clone, at minimum:

```bash
npm ci
npm test
npm run build
npm run build:backend
```

These script names exist in `package.json`: `test` runs `test:unit`, `test:origin`, `test:smoke` and `test:remote`; `build` is `tsc -b && vite build`; `build:backend` compiles the Electron/server code and prepares `dist/electron`.

**Note on `test:smoke`:** it does not start a server itself. As documented in `scripts/smoke-pty.mjs` it expects a Dopaterm server already running on `127.0.0.1:4040`, so `npm test` (which runs `test:unit`, `test:origin`, `test:smoke`, `test:remote` in that order) fails at the smoke step without one. (`test:origin` starts its own server on a free port.) So the server must be up before you run `npm test`:

```bash
node_modules/.bin/tsx server/index.ts & SRV=$!      # start the server directly, not via `npm start`
# wait until http://127.0.0.1:4040/ answers, then:
npm test
kill "$SRV"                                          # stop only your own PID; then confirm the port is free
```

Start it directly rather than through `npm start`: with `npm start`, `$!` is the npm process, not the server, and killing only that can orphan the real server on port 4040. Never kill by name or pattern (§15). If port 4040 is already in use by something that is not yours, do not kill it: the smoke test cannot be run as written (it hard-codes the port and ignores `DOPATERM_PORT`), so record `test:smoke` as `NOT RUN` with the reason and resolve it with the maintainer before releasing. Do not silently edit tests during a release.

Also run the packaged application on every platform you can (see §9).

Record every result with exactly one of:

```text
PASS
FAIL
NOT RUN
```

**`NOT RUN` is never `PASS`.** Do not summarize an unexecuted test as passing, and do not write "tests pass" when one of the four test scripts was not run.

## 7. Building artifacts

Build from the fresh clone at the tag (§5), after the test gate. The build output goes to `release/` (git-ignored).

```bash
npm run dist:mac    # macOS: .dmg and .zip   (= npm run dist -- --mac)
npm run dist:win    # Windows x64: NSIS installer and portable .exe
                    # (= npm run dist -- --win --x64 -c.npmRebuild=false)
```

Both run `npm run build && npm run build:backend && electron-builder`. `npm run dist` builds for the current OS only.

Facts to keep in mind (also see the README's "ビルド / パッケージ" section):

- `dist:mac` re-compiles `node-pty` for Electron, so it needs the Xcode Command Line Tools and Python 3. The produced architecture is the **host's**: building on an Apple Silicon Mac yields **arm64**. Intel (x64) and universal macOS builds are **not provided** unless explicitly added in a future release. Do not label an artifact `arm64` without checking.
- `dist:win` on macOS is a **cross-build** (it uses the bundled `node-pty` win32 prebuilds). See §9 for how to describe that.
- The README states the combination Node.js 20.19.4 / npm 10.8.2 as the one that has actually been verified. Prefer it; mention in the release notes if a different toolchain was used.
- Builds are not guaranteed to be byte-identical between runs. Do not expect a rebuild to reproduce a published checksum, and never substitute a rebuilt file into a published release (§1.3).

**All platform artifacts for a release must be built from the same commit `$SHA`.** If a platform is built on a different host, that host uses its own fresh clone at `vX.Y.Z` and re-verifies `HEAD == $SHA` and a clean status (§4 step 8) before building. If a platform cannot be built, the release ships without that platform's artifacts (and says so) — it does not ship an artifact from another commit to fill the gap.

### 7.1 Verifying the internal version

Before publishing, confirm that the packaged app reports `X.Y.Z`. For example:

- macOS: read `CFBundleShortVersionString` / `CFBundleVersion` in `release/mac-arm64/Dopaterm.app/Contents/Info.plist` (the unpacked app electron-builder leaves next to the DMG/ZIP).
- Any platform: read the `package.json` inside the unpacked `app.asar` (`release/mac-arm64/Dopaterm.app/Contents/Resources/app.asar`, `release/win-unpacked/resources/app.asar` — check the actual directory names in `release/`). `@electron/asar` is already in the dependency tree after `npm ci`. Use the copy in the clone's `node_modules` (do not let `npx` download one) and read without writing into the repository, e.g.:

  ```bash
  node -e "const a=require('<abs clone>/node_modules/@electron/asar');console.log(JSON.parse(a.extractFile('<abs path>/app.asar','package.json')).version)"
  ```

  (The `asar extract-file` CLI writes `./package.json` into the current directory — running it in the clone root would overwrite the tracked file. Don't.)
- The Windows installer and portable `.exe` themselves cannot be opened with `asar`; inspect the unpacked `win-unpacked` build instead. If the Windows internal version could not be inspected, record it as `NOT RUN`, say so in the release notes, and do not tick the "internal version" checklist item for Windows.

A mismatch between the internal version and `X.Y.Z` is a release blocker (§16).

## 8. Artifact naming

Artifact names must show **product, version, OS, architecture and package type**. The official names are:

```text
Dopaterm-X.Y.Z-macos-arm64.dmg
Dopaterm-X.Y.Z-macos-arm64.zip
Dopaterm-X.Y.Z-windows-x64-installer.exe
Dopaterm-X.Y.Z-windows-x64-portable.exe
```

The repository's electron-builder configuration does **not** set an `artifactName`, so the files written to `release/` use electron-builder's default names (for example `Dopaterm-X.Y.Z-arm64.dmg`, `Dopaterm-X.Y.Z-arm64-mac.zip`, `Dopaterm Setup X.Y.Z.exe`, `Dopaterm X.Y.Z.exe`; the exact defaults depend on the electron-builder version, so look at what was actually produced). Getting from those names to the official names is a **rename only**:

- Rename (or copy) the file; never alter its contents.
- Compute the SHA-256 after the final rename and record the mapping "builder output name → release name".
- Check each file's real architecture/type rather than trusting the name: e.g. run `file` on the executable inside the app (`Dopaterm.app/Contents/MacOS/Dopaterm`; `file` on a `.dmg`/`.zip` does not show it), and for Windows check the builder log for `--x64` and `file` on the unpacked `.exe`.

**Known inconsistency:** the README's download table (「インストール / ダウンロード」) still lists builder-style names such as `Dopaterm-<version>-arm64.dmg` and `Dopaterm.Setup.<version>.exe`, which differ from the official release names above (the actual v0.2.1 assets use the official names). The official names in this section are authoritative. The README table should be reconciled in a future release commit (before tagging); this document's introduction did not change it.

Adding a new architecture (e.g. macOS x64, Windows arm64) is a deliberate change: add it explicitly to this document, the naming list, the checksums and the release notes. Do not quietly attach one.

## 9. Platform verification semantics

Always distinguish these three states, per platform and per artifact:

```text
BUILD PASS      the artifact was produced
RUNTIME PASS    the artifact was actually executed and checked on that OS
NOT RUN         it was not executed / not checked
```

Example: Windows artifacts cross-built on macOS and never launched on Windows:

```text
WINDOWS BUILD:   PASS (cross-build on macOS)
WINDOWS RUNTIME: NOT RUN
```

Rules:

- Never write "Windows verified" (or "tested on Windows") unless the app was really run on Windows. A cross-build is a build result, not a runtime result.
- Likewise for any other OS/architecture combination.
- Emulators, Wine, WSL and architecture translation (e.g. Rosetta) do not count as runtime on the real target OS/architecture unless the notes name them as such.
- Say what "RUNTIME PASS" covered (e.g. "packaged app launches; local terminal runs a command; Japanese text displays"), so the claim is specific.
- If runtime is `NOT RUN` for a platform, the release notes must say so explicitly for that platform.

## 10. Signing and notarization

Release notes must state, for each platform: architecture, runtime verification status, signing status and, for macOS, notarization status. Be literal.

If no Apple Developer ID certificate was used (the current situation):

```text
macOS: Unsigned. Not notarized.
```

If the Windows binaries are not code-signed (the current situation):

```text
Windows: Unsigned. SmartScreen may warn.
```

- Never describe unsigned/unnotarized artifacts as signed, notarized, trusted or "verified publisher".
- Do **not** put in the official release procedure or release notes any instruction to permanently disable Gatekeeper, SIP or SmartScreen. (A per-file, user-initiated workaround may be referenced where the README already documents it, but it is not part of the release procedure.)
- If signing/notarization is added in the future, update this section and the release notes template first; record the signing identity type and `spctl`/notarization results as evidence.

## 11. Checksums

Compute SHA-256 for every official release asset (e.g. `shasum -a 256 <file>` on macOS).

Before upload, record for each artifact:

```text
artifact file name
size (bytes)
SHA-256
source commit (full SHA)
architecture
```

Then:

1. Upload the files to the **draft** Release (§14).
2. Compare GitHub's reported asset digest (`gh release view vX.Y.Z --json assets` shows `digest` and `size`) with your recorded SHA-256 and size.
3. Where possible, re-download the public assets and recompute SHA-256.
4. If anything does not match, **do not publish** (or, if already published, treat it as a release failure per §16).

Put the checksums in the release notes body.

## 12. Licensing gate

Before release, check:

```text
LICENSE
LICENSE-ASSETS.md
package.json "license"
third-party dependencies
```

Current state (verify, do not assume):

- The Dopaterm **source code** is licensed under **0BSD** (`LICENSE`; `package.json` has `"license": "0BSD"`).
- Dopaterm-specific images, the mascot character, the cabinet design, icons, and the demo visual assets are **not** covered by 0BSD; they stay governed by `LICENSE-ASSETS.md`.
- Third-party code and assets keep their own licenses. The packaged apps bundle third-party license documents (xterm.js, node-pty, ws, Electron/Chromium) — confirm they are present in the artifact.

Releasing is **not** an occasion to change license terms. Do not edit `LICENSE`, `LICENSE-ASSETS.md` or the `license` field as part of release work. If the files disagree with each other or with the release notes, stop (§16).

The release notes carry the same license summary as the previous release unless the maintainer has changed the licensing through a separate, explicit change.

## 13. Secrets and private-file gate

Before **and** after building, check the source tree and the artifacts for, at minimum:

- `.env` / `.env.*` files
- API keys and tokens (including `.dopaterm-token`)
- private SSH keys, `*.pem`, `*.key`
- tunnel credentials
- local config that contains secrets
- HANDOVER documents and internal reports
- development-only private files
- untracked local files
- local absolute paths from the maintainer's machine

Practical checks: `git status --short` is empty in the fresh clone; list the contents of the packaged `app.asar` and of the installer/portable payload where inspectable and compare with the expected file set (`dist/**/*` and `package.json`, per the `build.files` setting in `package.json`, plus `node_modules` production dependencies); grep the unpacked results for the patterns above.

If any secret or private file is detected: **stop the release**, do not upload, and report to the maintainer. Do not try to "just delete it from the artifact" and continue — the source commit may need to be revisited, and that means a new version.

## 14. Draft-first publication

Create the GitHub Release as a **draft** first, whenever possible. Use `gh release create vX.Y.Z --draft --verify-tag --notes-file <file> <assets...>` (or the equivalent): `--verify-tag` aborts if the tag does not already exist on the remote, so `gh` cannot silently create a new tag at the default branch's HEAD.

```text
create tag (on the final public commit)
        |
create draft Release
        |
upload artifacts
        |
verify file names
        |
verify sizes
        |
verify SHA-256 / GitHub digests
        |
verify source commit
        |
verify Release notes
        |
publish
```

Verify before publishing instead of fixing after publishing. In particular:

- the tag target (`git ls-remote --tags origin 'vX.Y.Z*'`, peeled `^{}` entry for an annotated tag) equals the recorded source commit;
- the Release's source-commit statement in the notes equals the same SHA;
- **GitHub's "Source code (zip)" and "Source code (tar.gz)" are generated from the tag**, so they are correct only if the tag target is that commit. **The tag must never be moved afterwards.**

### 14.1 Release notes must contain

- version and the **full source commit SHA**, stated as the single source for every binary and the source archives;
- downloads list with architecture for each artifact;
- per platform: BUILD / RUNTIME status (§9), signing and notarization status (§10);
- known limitations relevant to the release;
- license summary (§12);
- SHA-256 checksums (§11);
- a pointer to the previous release where relevant.

The notes must not claim anything that was not actually done (see §9, §10).

## 15. Process safety

Release verification must not harm other things running on the machine.

Forbidden:

```text
pkill -f ...
killall node
killall Electron
killall npm
```

or any other broad kill by name/pattern.

- Stop only **PIDs that you started yourself** (keep the PID when you launch something in the background).
- If a port is already in use, do **not** kill whatever holds it; use a different port where the tool allows it, or report the limitation (see the `test:smoke` note in §6).
- For DMG verification, unmount only the volume **you** attached (keep the mount point from your own `hdiutil attach`), and remove only temporary files you created.
- Do not modify the original development repository during release work.

---

## 16. When NOT to publish

**Do not publish** (or, if already published, declare the release failed and follow §1.3) when any of these holds:

- any required test is `FAIL` or `NOT RUN` (unless the maintainer explicitly waives it in writing in the release task)
- tag target mismatch
- source commit mismatch between any artifacts / the tag / the notes
- artifact checksum mismatch
- wrong architecture
- packaged app launch failure on a platform that the release claims as runtime-verified
- secret or private-file contamination
- license inconsistency
- a binary was built from a dirty or unpublished tree
- GitHub upload corruption
- `package.json`, `package-lock.json`, tag, filenames and packaged internal version do not all agree (§1.1)

Do not turn a failure into a PASS with "it's probably fine". Report the failure and the evidence.

## 17. Release checklist
